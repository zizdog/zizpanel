# 备份与恢复设计（已实现）

> 状态：**已实现** —— `internal/backup/{plan,run,apply,archive,manifest}.go`、
> `internal/store/restore.go`（`ReplaceFromBackup`）、`internal/web/api_backup.go`，
> UI 在计划任务页。本文只留归档格式、恢复流程与门禁；**实现细节与文件位置以代码为准**。

目标（用户原话）："网站配置和证书申请、反向代理，一定要有备份功能……就算重装面板，
也可以瞬间恢复。"

### C. **不进**备份

- 日志（`<DataDir>/logs`、`<brew>/var/log/nginx`、`~/www/_logs`）：可重建、体积大。
- 升级暂存包/看门狗（`<WorkDir>/upgrade/**`）：一次性产物。
- `RunDir`（pid/socket）、`~/.colima`（Docker VM，巨大可重建）。
- 备份输出目录自身（否则越备越大）。
- `~/www` 站点文件：**用户数据**，不是面板自有资产（但面板确实会创建/chown 站点根目录、
  写默认站点占位页与 `_acme`/`.well-known`、`_logs`，见 `internal/web/api_sites.go:525-535`、
  `internal/sites/defaultsite.go:62-67`、`api_certs.go:104`）。要不要一起打包见第七节问题 1。
- `sessions` 表：可以带上，但**恢复后必须清空**（见第三节第 4 步）。

### D. 与**既有定时备份**的关系（重要：不要另造一套）

面板**已经有**一个定时备份：计划任务类型 `backup`，可选 targets
`sites` / `mysql` / `nginx` / `panel`，输出单个 tar.gz 到 `BackupDir`
（默认 `/opt/zizpanel/work/backup`），按 `keep_days` 清理
（`internal/scheduler/launchd.go:205-275`；`<WorkDir>/backup` 见 `config.go:674`）。

它覆盖了"备份"这一半，但有 4 处**必须一起修**的缺陷：

1. **没有一致性保证，也没有完整性元数据**：`panel` target 直接 `tar` 整个 `<DataDir>`
   （`launchd.go:262-268`）。本机现存归档实测结构＝"外层 tar.gz 套 `panel.tar.gz` + `nginx.tar.gz`"，
   `panel.tar.gz` 里确实带了 `panel.db`、`panel.db-wal`、`panel.db-shm` —— 但三个文件是
   **分别**读出来的，不是同一瞬间的快照，而且**没有 manifest / 没有任何校验和**，
   事后无法判断它自不自洽。→ 改成 `VACUUM INTO`（单语句原子快照）+ manifest/sha256。
2. **路径写死**：`/opt/zizpanel`、`/opt/homebrew` 硬编码
   （`launchd.go:213,243,262`；兜底值同样写死在 `scheduler.go:225-226`），
   `ZIZPANEL_ROOT` 重定位或 Intel 前缀（`/usr/local`）下会备错东西或什么都不备。
3. **任务选项根本没落库**：`cron_jobs` 表**没有** `backup_targets`/`backup_dir`/`keep_days`
   列（`store.go:226-239`），而 `Repository.Create/Update` 只写
   `name/kind/schedule/command/work_dir/enabled`（`scheduler.go:307-330`）→
   用户选的备份范围/目录/保留天数**面板一重启就回落到默认**
   （`scheduler.go:216-229`：`sites,nginx,panel` + `/opt/zizpanel/work/backup` + 7 天）。
   "我明明选了 mysql，它却没备"就出在这里 —— 属于**谎报成功**那一类。
4. **没有"恢复"**：这次要补的正是恢复（+ 上传恢复 + 一键回滚）。

结论：**扩展现有 backup 任务（顺手修上面 4 条）+ 新增恢复**，而不是并行做第二套备份。

### E. 敏感度

归档里含 **面板配置 + 面板下发过的数据库明文口令**（`db_credentials` 表，`store.go:255` 注释
说明这是"能显示数据库密码"的唯一诚实做法）+ ACME 账号私钥 + 站点私钥。
→ 权限 `0600`，界面上必须明确写："备份含明文口令，请当机密文件保管。"

## 二、归档格式与完整性

- `tar.gz` + `manifest.json`：`format` / `created_at` / `panel_version` / `schema_tables`
  / `contains_secrets` / 每个文件的 `path,size,sha256`。
- 恢复前逐条校验 sha256，任何一条不符 → **整包拒绝**，不做部分恢复。
- ⚠️ 面板**没有**读 `schema_version` 做判断的逻辑（迁移末尾写 `settings.schema_version='3'`，
  但当前代码从不读它，`internal/store/store.go:314`）→ 兼容性判据必须靠**表/列对比**，
  不能靠这个字段。

## 三、恢复流程（关键：**不替换正在使用的 panel.db**）

> 依据：驱动内嵌 SQLite **3.46.0**（`modernc.org/sqlite v1.34.4`，
> `lib/sqlite_darwin_amd64.go:2842`），`ATTACH` 与 `VACUUM INTO`（≥3.27）都可用；
> 本机已用同语义 SQL 实测："逐表 DELETE+INSERT + 恢复 sqlite_sequence"提交成功，
> 注入主键冲突时**整事务回滚、目标库一字未变**。

1. **上传/选择归档** → 校验 manifest、逐文件 sha256、表/列兼容性。
   备份库更旧（缺列）→ 允许，但必须走第 3 步的"重放迁移"；
   备份库有当前代码不认识的表/列（备份比程序新）→ **拒绝**并说明。
2. **恢复前自动快照**（回滚唯一凭据）：`VACUUM INTO` 出的一致性库 + `config.json` +
   `certs/` + `acme/credentials.json` + nginx（`nginx.conf`/`vhosts/`/`conf.d/`）+ php 片段 +
   相关 launchd plist。注意 `VACUUM INTO` 会占住**唯一**一条数据库连接
   （`store.go:45` `SetMaxOpenConns(1)`）→ 期间面板其它请求排队，这一步要短。
3. **数据库**（新增 `Store.ReplaceFromBackup(...)` 封装，调用方不碰 pragma）：
   - `db.Conn(ctx)` 拿专用连接；**事务外**执行 `PRAGMA foreign_keys=OFF`
     （该 pragma 是连接级且**事务内切换无效**）；`ATTACH` 备份库；
   - 一个事务内：`DELETE` + `INSERT` 逐表复制，顺序 `users` → `sessions`（唯一外键
     `sessions.user_id REFERENCES users(id) ON DELETE CASCADE`，`store.go:93`）→ 其余表；
     再恢复 `sqlite_sequence`（8 张 AUTOINCREMENT 表：users/sites/proxies/services/api_keys/
     audit_logs/cron_jobs/certificates）；
   - `COMMIT` → `PRAGMA foreign_keys=ON` → `PRAGMA foreign_key_check` 必须为空 →
     **重放 `migrate()`** 给旧库补新列（`store.go:292-312` 的 `ensureColumns`）。
4. **清空 `sessions`**：会话是每请求查库（`internal/web/middleware.go:120-135`、
   `internal/auth/auth.go:453`），恢复旧库会把备份时的旧会话重新激活 ——
   必须清掉（强制重新登录），否则等于把认证状态回退到过去。
5. **证书与 ACME**：写回 `<DataDir>/certs/**` 与 `<DataDir>/acme/credentials.json`
   （在 DataDir 白名单内，走文件接口或 helper；注意属主/权限）。
6. **nginx / PHP 环境按语义重建**（不整份还原生成物）：
   - vhost：逐个走 helper `vhost-write`（**唯一**带 `nginx -t` + 失败回滚的通道，
     `priv.go:386-423`）；
   - `conf.d` 的 map/include：`nginx-ensure-env`（`priv.go:1348-1390`）；
   - nginx.conf 参数：`nginx-tuning-write`（结构化、自带校验，`priv.go:1476+`）；
   - PHP 片段：`sites.EnsurePHPLimits`。
   最后 `nginx -t` + reload（复用面板既有的"写盘→校验→reload→请求级复核"通道，
   见 `internal/web/api_sites.go:216-260`）。
7. **计划任务**：按恢复后的 `cron_jobs` 重放 launchd 注册/注销
   （`internal/scheduler/scheduler.go` + `launchd.go`）。
8. **`config.json`**：`Server.Cfg` 是启动时加载的（`cmd/zizpanel/main.go:382`）→
   恢复它**必须重启面板**才生效。建议默认**不恢复**（保持本机身份：后缀/端口/证书），
   由用户显式勾选"连同面板配置一起恢复（会重启面板）"（见第七节问题 4）。
9. **如实回读**：站点数、证书记录数、反代规则数、cron 条数、`nginx -t` 结果、
   `foreign_key_check` 结果，以及任何"没恢复上"的清单。失败就说清"已回滚"还是"部分应用"。

## 四、回滚

用第三节第 2 步的快照走同一条恢复路径。最少必须包含（依据 subagent 评估）：
① 一致性 panel.db（不要 `cp` 单文件，WAL 里有未 checkpoint 的数据；
   用 `VACUUM INTO`）② `config.json` ③ `certs/` + `acme/credentials.json`
④ nginx：`nginx.conf`（已有 `.zizpanel.bak`）+ `vhosts/` + `conf.d/`
⑤ php 片段 ⑥ launchd plist（cron 重放会重写它们）。

## 六、测试与门禁（计划）

1. manifest：生成/校验；坏 sha256、缺文件、未知表必须整包拒绝。
2. 数据库恢复：临时目录造源/目标库（含 `sessions` 外键、AUTOINCREMENT），断言
   逐表一致、`sqlite_sequence` 一致、`foreign_key_check` 为空；
   **失败注入**（唯一键冲突）后目标库一字未变。
3. 旧库兼容：造一个缺新列的旧库 → 恢复后 `migrate()` 补列成功、接口能读写。
4. 会话：恢复后旧 cookie 必须失效（`GET /api/v1/session` → 401）。
5. 半应用防护：vhost 写坏时 `nginx -t` 失败必须回滚，`nginx -T` 里不能出现半新半旧。
6. **清单覆盖门禁**：测试遍历"应当进备份的路径清单"，代码新增数据文件却没加进清单就变红。
