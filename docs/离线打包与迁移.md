## 1. 离线包格式（NAS 侧）

### 1.1 布局

```
<镜像基址>/offline/<app-id>/index.json                ← 有哪些版本、current 是哪个
<镜像基址>/offline/<app-id>/<version>/manifest.json    ← 本应用安装所需的**全部**文件
<镜像基址>/offline/<app-id>/<version>/artifacts/...     ← 真实文件（sha256 实算）
```

- `<version>` 优先用**真实版本号**（brew 类是 `stable + revision`，如 `9.0.1_1`；release 二进制是 tag，如 `v0.71.0`）；
  实在没有版本概念的（如 iopaint 的模型）用 `current`。
- `/offline/` 是 NAS 上的**静态目录**（`/vol2/zizpanel-mirror/offline/`，容器把整个
  `/vol2/zizpanel-mirror` bind mount 成 `html` 根）→ **不需要改 nginx.conf、不需要重启任何容器**，
  `http://192.168.1.8:8090/offline/...` 直接可读（实测 200）。
- 因此离线包与 `apps/`、`models/`、`brew/` 是**并列的静态路径**，也不会和别的代理正在改的
  `nginx.conf`（pypi/docker 那些 location）抢同一份文件。

### 1.2 manifest.json 字段

| 字段 | 含义 |
|---|---|
| `schema` | `zizpanel.offline/v1`（对不上的版本要明确拒绝，不许硬解） |
| `app` / `name` / `version` | 应用 ID、显示名、**真实版本** |
| `install_method` | `brew` / `binary_release` / `compose` / `site` / `panel_installer` / `colima` |
| `brew` | 仅 brew 类：`formula` / `api_dir` / `bottle_dir`（下面 §1.4 讲怎么用） |
| `docker_images` | 仅 compose 类：compose 文件里引用的镜像（原样，未加 registry 前缀） |
| `artifacts[]` | **本应用安装所需的每一个文件**，见下 |
| `missing[]` | 构建时**取不到**的文件（逐条，含原因）—— 不许静默跳过 |
| `warnings[]` | 取到了但有问题的（如镜像缺 OCI manifest，brew 会退化成 full relocation） |
| `gaps[]` | **设计上还没镜像**的东西（如 compose 镜像 tar、PyPI 依赖闭包） |
| `totals` | `{artifacts, bytes, missing}`，与 artifacts/missing 逐个对齐 |

`artifacts[]` 里每个文件一定有：

| 字段 | 含义 |
|---|---|
| `kind` | `brew_bottle` / `brew_manifest` / `brew_formula_json` / `pip_wheel` / `model` / `site_tarball` / `github_binary` / `docker_image_tar` / `vm_image` / `other` |
| `path` | 在离线包里的**相对路径**（= 离线安装时它必须被 serve 的路径），如 `artifacts/brew/ffmpeg-9.0.1_1.arm64_sequoia.bottle.tar.gz` |
| `url` | **上游地址，仅作参考**（离线安装永远不用它；留着是为了缺件时告诉人去哪补） |
| `source_url` | 这次实际从哪取的（正常是 NAS 镜像自己） |
| `sha256` | ★ **下载落盘后真算出来的**，不是抄的（见 §2.3） |
| `size` | 实测字节数 |
| 其它 | `formula` / `tag` / `pkg_version` / `bottle_rebuild` / `note`（brew 类） |

### 1.4 brew 类怎么"离线装上"（不是猜的，是读 brew 源码 + 真机日志定的）

把下面两个环境变量指到离线包，`brew install` 就完全不碰外网（**已在断网的 mini 上跑通，见 §4**）：

```
HOMEBREW_API_DOMAIN    = <base>/offline/<app>/<ver>/artifacts/brew/api
HOMEBREW_BOTTLE_DOMAIN = <base>/offline/<app>/<ver>/artifacts/brew
```

对应的文件名规则（逐行核对 mini 上 Homebrew 7.0.2 的
`bottle.rb` 的 `Bottle::Filename`、`github_packages.rb` 的 `version_rebuild`、
`utils/bottles.rb` 的 `path_resolved_basename`，并用 NAS 上 brew 自己的 access log 对照）：

```
pkg_version  = versions.stable + ("_" + revision if revision > 0)
平铺瓶文件名  = "<name>-<pkg_version>.<tag>.bottle[.<bottle_rebuild>].tar.gz"
OCI manifest = "<name 里 @→/ +→x>/manifests/<pkg_version>[-<bottle_rebuild>]"
```

真机对照（NAS access log，brew 自己发的请求）：

| 公式 | revision / bottle rebuild | brew 请求的 manifest | brew 请求的瓶 |
|---|---|---|---|
| ffmpeg | 1 / 0 | `/brew/ffmpeg/manifests/9.0.1_1` | `/brew/ffmpeg-9.0.1_1.arm64_sequoia.bottle.tar.gz` |
| abseil | 0 / 1 | `/brew/abseil/manifests/20260817.0-1` | `/brew/abseil-20260817.0.arm64_sequoia.bottle.1.tar.gz` |
| mysql@8.4 | 4 / 0 | `/brew/mysql/8.4/manifests/8.4.11_4` | `/brew/mysql%408.4-8.4.11_4.arm64_sequoia.bottle.tar.gz` |
| php@8.2 | 0 / 0 | `/brew/php/8.2/manifests/8.2.33` | `/brew/php@8.2-8.2.33.arm64_sequoia.bottle.tar.gz` |

> ⚠️ **坑（差点误判成"镜像缺件"）**：只看 `versions.stable` 是不够的，必须带 `revision`。
> 第一版漏了 `revision`，把 ffmpeg 算成 `ffmpeg-9.0.1...`（真名是 `9.0.1_1`），于是报"镜像上没有这个瓶" ——
> 而镜像上其实有。少一个 revision 就会把一个装得上的应用误报成缺件。
>
> ⚠️ **坑（HTTP 侧核对抓出来的）**：`openssl@3` 的瓶，brew 请求的是 `openssl%403-...`（URL 编码），
> nginx 会把 `%40` 解回 `@`，**落盘名是 `openssl@3-...`**。第一版把编码后的名字当成落盘名，
> 磁盘上真出现了一个叫 `%40` 的文件，**本地核对全过、HTTP 侧立刻 404**。
> 这条正好说明"必须从 HTTP 侧重下重算"这条纪律的价值。

## 2. 打包工具

### 2.1 组成

| 文件 | 作用 |
|---|---|
| `tools/build-offline-bundle.sh` | 入口：选应用、取件、算 sha256、写清单、上传 NAS、HTTP 侧核对、缺件对账 |
| `tools/offline-bundle-lib.py` | 按计划取件 + 实算 sha256 + 写 manifest/index |
| `tools/offline-brew-resolve.py` | 把一个 brew formula 展开成**依赖闭包**的文件清单（含上面那套命名规则） |
| `internal/services/offline_plan.go` | `OfflinePlan()`：从代码目录/注册表生成 27 个应用的**打包计划**（纯函数，不联网） |
| `cmd/zizpanel-assets plan` | 把计划打成 JSON（`apps` 子命令保持原样，兼容 `sync-nas-apps.sh`） |

设计要点（都是踩过的坑）：

- **计划从代码生成，不在脚本里手抄** —— 手抄的那份在加应用/升版本时一定会漏。
- **sha256 一律对落盘文件重算**；上游清单里声明的只用来**判等**，不等就判缺件并失败。
- **缺件逐条列出**，最后按"计划制品数 = 磁盘文件数"对账，并且选中应用数 = 汇总条数。
- **ssh 一律 `-n` + `</dev/null`**：`sync-nas-apps.sh` 曾因为 `ssh` 在 `while read` 里吞掉 stdin
  而静默跳过应用却报成功。
- `--dry-run` 只解析（含真实 HEAD 取体积）不下载，可用来做缺口盘点。

### 2.2 用法

```bash
# 1) 只看计划与已知缺口（不联网下载）
bash tools/build-offline-bundle.sh --list

# 2) 只解析体积（会向镜像发 HEAD，不落盘）
bash tools/build-offline-bundle.sh --dry-run --app ffmpeg

# 3) 本地打包（下载 + 实算 sha256 + 写 manifest；不上传）
bash tools/build-offline-bundle.sh --app frpc --app ffmpeg --stage /tmp/stage

# 4) 打包并上传到 NAS（上传后逐个制品从 HTTP 侧重下重算 sha256）
NAS_PASS='…' bash tools/build-offline-bundle.sh --app frpc --app ffmpeg --upload

# 5) 事后验收（只读 NAS 上的 index/manifest，重下重算）
bash tools/build-offline-bundle.sh --verify ffmpeg
```

```go
//      补法：bash tools/build-offline-bundle.sh --app <应用> --upload … 或关掉这个开关"
```

| 13 | `internal/services/basedep.go` | 基础依赖（ffmpeg 等）安装 | 走 brew（同 #1） | 同 #1 |

**接线的推荐姿势**（改动最小、不动默认行为）：在每个回落点之前插一行

```go
mirrorURL := m.appAssetURL(spec.ID, spec.Tag, spec.Asset)   // 或该来源的镜像地址
if err := m.MirrorOfflinePreflight(ctx, "frpc 安装包", mirrorURL); err != nil {
    return err
}
```

非离线模式下它是 no-op；离线模式下它会拦住回落并给出可读的错误。

### 3.4 一个必须让用户知道的部署事实

**面板默认的 `mirror_base` = `https://mirror.zizdog.com:8888` 解析到的是公网 IP
（`110.177.80.110`，实测），不是 NAS 的局域网地址。** 所以：

- 平时（有外网）它没问题，走公网绕一圈回来；
- **真离线时它不通**（实测：断外网后 `https://mirror.zizdog.com:8888/` → `http=000`，
  而 `http://192.168.1.8:8090/` → `200`）。

结论：**离线/迁移场景必须把 `mirror_base` 改成 `http://192.168.1.8:8090`（NAS 局域网地址）**，
否则"镜像优先"会在第一步探测就失败、然后回落到公网 —— 表现为"装不上"而不是"用镜像装上了"。
本次断网实测就是先把 mini 的 `mirror_base` 临时改成 `http://192.168.1.8:8090` 才跑通的，
测完已改回 `https://mirror.zizdog.com:8888`（见 §4.6）。
