# 新增一个应用到「应用市场」的完整工作流

> 这份文档是给**未来的你（或下一个会话）**看的操作手册。
> 目标：**加一个应用 = 填空 + 一条命令告诉你缺什么**，而不是"一个一个踩坑"。
>
> 用户的原话（2026-09-16）：
> > "对于应用市场，应该有能用高效的工作流，如果以后每加一个应用都要一点一点慢慢调试，
> > 那这个应用市场就没什么实用价值了。"
>
> 三层工具：
>
> | 层 | 是什么 | 在哪 | 联网 |
> |---|---|---|---|
> | 1 | 声明（填空的地方） | `internal/services/market_downloads.go` | 否 |
> | 2 | 静态门禁（不变量） | `MarketInvariantProblems()`，由 `go test ./internal/services -run TestMarket` 跑 | 否 |
> | 3 | 在线审计（一条命令审全部） | `make market-audit` | 是 |
> | 4 | 真机安装验收 | `make market-audit-verify ARGS="<url> <user> <pass>"` → `tools/market-install-verify.py` | 是（会真的装） |
>
> 第 2 层已经在 `make check` 里（因为 check 会跑 `go test`）。第 3 层不进硬门禁：
> 它会因为**真实缺口**（镜像站上还没同步某个包）红灯，那是体检报告，不是"代码写错了"。

## 加一个应用 = 5 步

```bash
# ① 选路 + 找证据（不改代码，只是查）
#    能原生就原生：brew formula 或官方 darwin-arm64 预编译产物；否则 Docker，但镜像必须自带 linux/arm64
brew info --json=v2 <formula> | python3 -c 'import json,sys;print(json.load(sys.stdin)["formulae"][0]["versions"])'
curl -sS "https://api.github.com/repos/<owner>/<repo>/releases/latest" | python3 -c 'import json,sys;[print(a["name"],a["size"],a["browser_download_url"]) for a in json.load(sys.stdin)["assets"]]'
docker manifest inspect --verbose <image>:<tag> 2>/dev/null | head -40   # 看有没有 linux/arm64

# ② 写目录条目（internal/services/catalog.go）—— 这一条要看 AGENTS.md 铁律 10

# ③ 在 internal/services/market_downloads.go 里填空：一个 MarketApp + 每个下载点一个 MarketDownloadPoint
#    把这一步当成"回答 6 个问题"，不是"写文档"（模板见下一节）

# ④ 一条命令：静态门禁 + 在线审计，只审这一个
make market-audit ARGS="--only <新应用ID>"

# ⑤ 真机装一遍（**替代不了**）
make market-audit-verify ARGS="https://127.0.0.1:8443/<面板后缀> <user> <pass> --only <新应用ID>"
```

> ⚠️ 基址必须带**面板安全后缀**（接口在 `/<后缀>/api/v1/...`，根路径是 404）；
> 写接口要 CSRF 双提交（`X-CSRF-Token`），`tools/market-install-verify.py` 已自动带。

四条命令里的前三条都能离线/本地完成；**第 ⑤ 步必须真机**（见文末"哪些事仍然必须真机做"）。

## 第 ① 步的判据是**三层**，不是两层（2026-09-17 补）

铁律 10 说的是"能原生就原生，不能原生再 Docker"，但 2026-09-17 加 Miniflux / Syncthing
时发现中间还有一层：**"有 brew formula"或"有官方 release 产物"只是**分发**上的原生，
不代表**装完就能用**。**

```
① brew formula 存在？        → 用它（但要接着问第 ② 步）
   没有 → 有官方 darwin-arm64 release 产物？ → 用 tarball 轨（同样要问第 ② 步）
② 装完还需要"收尾"吗？        → 需要就不是"填空"，是自研安装器
     · 需要数据库、要建库建角色？            （Miniflux）
     · 需要面板写配置文件 / 生成初始口令？    （Miniflux / Syncthing）
     · 需要改应用自己的绑定地址或认证？        （Syncthing 的 GUI）
   任何一条为真 → 加 `PanelInstaller`，写 `InstallXxx`，并按
   `handleMarketInstall` 分流的写法接上；**卸载侧要在 `installerPlan` 与 `UninstallApp`
   两处都登记**（漏一处 = 市场点了没反应 / 删不掉）。
③ 两条原生路都不行 → Docker（镜像必须自带 linux/arm64）。
```

真实例子与代价：

| 应用 | 有 formula？ | 装完能直接用？ | 结论 |
|---|---|---|---|
| Miniflux | ✅ 有 service 块 | ❌ 没有配置文件起不来；必须 PostgreSQL | 自研安装器（约 700 行，含建库/迁移/初始口令/自检） |
| Syncthing | ✅ 有 service 块 | ⚠️ 起来了，但 GUI 只绑 127.0.0.1，局域网打不开 | 自研安装器（改绑定 + 随机口令 + 验收） |
| Alist | ❌ 从未进过 homebrew-core | ✅ 首次启动自建 data/ 并打印初始口令 | 纯填空（tarball 轨 + 一条"从日志抓初始口令"的收尾） |

另外两条同轮学到的：

- **上游只发 md5 时不要假装校验过 sha256**：把 `Checksum.SHA256` 留空 + 写清原因，
  自己实算一遍 sha256 与上游 md5 互证，并写进镜像 `manifest.json`（见坑 119）。
- **新条目往往需要新的目录字段**：brew 应用的配置文件不在家目录里（
  `/opt/homebrew/etc/miniflux.conf`、`~/Library/Application Support/.../config.xml`），
  `ConfigPath` 支持绝对路径与 `~/` 之后服务详情才有「📝 编辑配置文件」（见坑 121）。
- **跟已有条目抢同一个端口/数据目录时**（2026-09-20 加 MariaDB）：目录门禁默认要求
  端口唯一，只有"同一个组件位的两个引擎"（MySQL 8.4 / MariaDB 共用 3306 与
  `<brew>/var/mysql`）才允许，判据是 `internal/services/lnmp_engine.go` 的
  `portSharingAllowed`。这种情况**必须**配一个可注入的互斥护栏：装 A 前检查 B 是否
  已装/在跑，对方在跑就拒绝并给出路 —— **绝不替用户停正在运行的服务**。
  同形的 brew 条目（有 service 块）不需要 `PanelInstaller`，通用 brew 流程已覆盖装卸。

## 填空题：一个下载点要回答什么

`market_downloads.go` 里，一个应用 = 一个 `MarketApp`，它下面每个**网络下载点** = 一个
`MarketDownloadPoint`。逐字段填：

| 字段 | 填什么 | 去哪找 |
|---|---|---|
| `Purpose` | 用途枚举：`brew_bottle` / `brew_installer` / `brew_git` / `release_binary` / `docker_image` / `pip_package` / `model_file` / `site_source` / `clt` / `vm_image` | 看安装代码到底执行了什么命令 |
| `Label` | 人读的一步（"brew install python@3.11"）；它会直接出现在审计表里 | 安装代码里的那一步 |
| `Upstream.ID` | formula 名 / 镜像名 / `github.com/repo@tag/asset` / PyPI 包名 | `brew info`、catalog 的 `ComposeYAML`、`binary_release.go` 注册表 |
| `Upstream.URL` | 可直接探测的地址（release 二进制 / 站点源码 / 模型文件 / VM 镜像） | GitHub API 的 `browser_download_url` |
| `Upstream.Repo/Tag/Asset` | GitHub release 三元组（有就填）——填了会被拿去和 `ReleaseBinaryAssets()` 注册表比对，URL 也会被自动核对 | `internal/services/binary_release.go` |
| `Upstream.Size` | **实测或上游声明**的字节数；不知道就写 0（**不许猜**），非 0 时 Note 里要写清来源 | `curl -sSI <url>` 的 `content-length` |
| `Upstream.Note` | 上游限制、回落顺序、已知不一致 | 读安装代码 |
| `NAS.State` | `mirrored`（有确定路径）/ `missing`（**该镜像但还没有**）/ `not_needed`（镜像了也没收益） | 见下 |
| `NAS.Path` | 镜像站**相对**路径（相对镜像基址，不以 `/` 开头） | release 二进制：`apps/<id>/<tag>/<asset>`；brew：`brew`；docker：`docker` |
| `NAS.Reason` | `missing` / `not_needed` 必填，**≥20 字**，要带实测数字或架构事实 | — |
| `Timeout` | 代码里**真实存在**的超时 | 在安装代码里 grep `WithTimeout` / `time.Minute` |
| `TimeoutReason` | `Timeout==0` 时必填：为什么真的没有超时 | — |
| `Required` | 失败会不会让安装失败 | 看错误是 return 还是只写 warning |
| `OptionalImpact` | `Required=false` 时必填：少掉什么能力 | 看 warning 文案 |
| `Checksum.Asset` | 校验依据（清单文件名 / "OCI manifest" / "manifest digest"） | 上游有没有 `checksums.txt` |
| `Checksum.UpstreamFile` | 上游校验清单的**文件名**（没有就空） | `ReleaseBinaryAssets()` 的 `ChecksumAsset` |
| `Checksum.SHA256` / `Source` | 已知的完整期望值 + 来源；**没有就留空**，由在线审计去取 | 镜像站的 `manifest.json`、上游 `checksums.txt` |
| `Checksum.Note` | 没有校验时必须写清"为什么没有" | — |
| `ARM64` | 怎么验证这个下载点在 arm64 上可用的（**写验证方式**，不是"应该可以"） | `docker manifest inspect`、资产文件名 `*_darwin_arm64.*`、`file -b` |
| `Note` | 其它要交代的（回落顺序、已知坑） | — |

### "镜像站优先？"这一格怎么填（最容易填错的一格）

- **`mirrored`**：镜像站上有一个确定路径。填 `Path`，审计会**真的去 HEAD/Range GET 它**。
- **`missing`**：**该镜像但还没镜像**。填 `Reason` 说清"缺什么 + 建议怎么做"。
  审计报 ❌。这是**默认答案**——不要因为不好意思就改成 `not_needed`。
- **`not_needed`**：镜像了也没有收益。填 `Reason`，**必须带实测数字或架构事实**，
  例如"只有 33,604 B，官方直连实测 200 / 0.5 s，且已有两条回落"。
  **不许**写"不需要"三个字：静态门禁要求理由 ≥20 字，`make market-audit` 每次都会把
  所有 `not_needed` 的理由打进报告，供人复核。

> 为什么这么设计：把缺口写成"不需要"是最容易发生的谎报。所以状态是三态、缺口是 ❌、
> 理由要给人看。**"谎报成功比没做更糟"**。

## 一次完整的示例：squoosh

squoosh 是目录里最麻烦的一个：**上游没有官方镜像**（`GoogleChromeLabs/squoosh` 仓库里
没有任何 Dockerfile），只能用社区镜像；而且社区镜像还有加速源的坑。走一遍：

**① 查上游有没有官方镜像 / brew / release**

```bash
# 官方仓库里没有镜像发布流程（只有编译 wasm 编解码器用的 codecs/*.Dockerfile）
curl -sS https://api.github.com/repos/GoogleChromeLabs/squoosh/contents/.github/workflows | grep '"name"'
# 没有 brew formula、没有 darwin 预编译产物 → 只能 Docker
```

**② 找社区镜像并核对 arm64 证据**

```bash
# 固定版本（不跟 latest 漂）：1.1.0
docker manifest inspect --verbose pjmeca/squoosh:1.1.0 | grep -E '"architecture"|"os"'
# → linux/amd64、linux/arm64、linux/arm/v7（两个 tag 的 arm64 digest 相同）
```

**③ 填 `catalog.go`**（Kind/ComposeYAML/UI 头等）：这里 `ComposeYAML` 用 `composeTemplate("squoosh", "pjmeca/squoosh:1.1.0", 8085, 80, ...)`，
**绝不写 `platform:`**；`AppUI.Headers` 要带 COOP/COEP（SharedArrayBuffer 要求
`crossOriginIsolated`，少了这两个头页面只会 "Failed to load app"，而所有请求都是 200）。

**④ 填 `market_downloads.go`**

```go
{
    ID: "squoosh", Kind: KindCompose, ComposeImage: "pjmeca/squoosh:1.1.0",
    Runtime: MarketRuntime{Mode: MarketRuntimeContainer, LabelSource: "目录 Kind=KindCompose"},
    Downloads: []MarketDownloadPoint{
        dockerImagePoint("pjmeca/squoosh:1.1.0", 20*time.Minute,
            nasMirrored("docker"),
            "arm64 证据：Docker Hub 经加速源读同一份 index → linux/amd64、linux/arm64、linux/arm/v7"+
                "（实测层合计 30.8 MiB）。⚠️ daocloud 明确拒绝该镜像（DENIED … not in the allowlist），"+
                "1panel / dockerproxy 能服务它 —— 所以 Docker 加速源必须是有序列表且不止一条"),
    },
},
```

**⑤ 一条命令审它**

```bash
make market-audit ARGS="--only squoosh"
```

这一步会真的去 `pjmeca/squoosh` 取 manifest，判断有没有 `linux/arm64`。
如果它红了，看下一节。

**⑥ 真机装一遍**

```bash
make market-audit-verify ARGS="https://127.0.0.1:8443/<面板后缀> <user> <pass> --only squoosh"
```

## 每条不变量为什么存在（对应真实踩过的坑）

| 不变量 | 为什么 |
|---|---|
| 每个下载点必须声明超时（或写清为什么没有） | "没有超时 → 永远挂住"在历史上多次发生；Colima 的 5 分钟配 71 分钟的下载就是这么被掐断的 |
| compose 不许出现 `platform:`，且必须有 arm64 证据 | 铁律 10：`platform: linux/amd64` / Rosetta 转译在 M 系列上会静默降级或跑不起来 |
| 有服务语义的应用必须显式回答 `launchd/container/site/none` | "装好了但服务没起"、"市场显示未安装"都来自服务语义没写清 |
| 每个下载点必须回答"镜像站优先？"（不许留空默认通过） | 留空默认通过 = 审计全绿而缺口一个没解决 |
| 声明的目录字段必须与 `Catalog()` 一致 | 目录改了声明没改，声明就成了一份过期文档，下一步就有人照着它踩坑 |
| release 二进制必须与 `ReleaseBinaryAssets()` 一致 | 版本/文件名错位会表现为"条目在市场里、装的却是别的东西" |
| `Checksum.SHA256` 必须带 `Source` | 来源不明的 sha256 出过"镜像永不命中、静默回落慢源"的事故 |
| `Required=false` 必须写 `OptionalImpact` | IOPaint 的 ffmpeg 失败只写 warning，用户以为"装好了"，其实视频去水印不可用 |
| 站点源码的候选 URL 必须与目录 `SiteApp.DownloadURL/MirrorURLs` 一致 | Typecho 的备址（jsdelivr）实测已经 404，等于单点；改地址时声明必须同步 |

## 如果审计报 ❌ 怎么办

先看 ❌ 后面那句"缺什么"，再对号入座：

| 报错 | 含义 | 修法 |
|---|---|---|
| `镜像站缺口（声明里就是这么写的）` | 这一步该镜像但还没镜像 | 补镜像，或证明它确实不该镜像（改成 `not_needed` + 带实测数字的理由） |
| `镜像站缺口` + 用途 `release_binary` | 镜像站上没有这个包 | `tools/sync-nas-apps.sh`（它从 `ReleaseBinaryAssets()` 读清单，加应用会自动带上） |
| `镜像站缺口` + 用途 `vm_image` | 镜像站上没有 Colima guest 镜像 | 同步 `apps/colima-core/<ver>/<file>` 与 `.sha512sum`；**版本要从 colima 二进制取，别写死**（当前 v0.10.4 已就位） |
| `镜像站缺口` + 用途 `site_source` | 站点源码没镜像 | 同步到 `apps/<id>/<ver>/`，并把候选顺序改成 镜像优先（当前代码只试 `DownloadURL + MirrorURLs`） |
| `镜像站缺口` + 用途 `pip_package` | 镜像站没有 `/pypi` | 给镜像站加 pypi 反代；不加就承认它是缺口（清华源实测 4.6 MB/s，不致命） |
| `镜像站缺口` + 用途 `clt` | CLT 载荷没预置（只有清单） | 用 `tools/sync-clt-mirror.sh` 把 `index.json` 里声明的 pkg/分片预置到 `zizpanel/clt/<build>/`（当前镜像站：632 MB / 21 片） |
| `镜像站上返回 HTTP 404` | 路径写错了，或同步工具没同步这个目录 | 对照 `apps/<id>/<tag>/` 布局；同步工具不会造目录 |
| `manifest 里没有 linux/arm64` | 违反铁律 10 | 换一个自带 arm64 的镜像/tag；**不许**加 `platform:` 绕过 |
| `取不到 manifest` | 该 registry 不可达，或自建镜像站不覆盖它 | 让它走 Docker Hub（换个 image 名）或直连可达的 registry；否则就是真不能上架 |
| `实算 sha256 ≠ 上游 checksums` | **内容对不上，大概率是同步错了/被改过** | 重新同步；绝不放宽校验 |
| `镜像站上的字节与它自己的 manifest 不一致` | 镜像站上的文件坏了或 manifest 过期 | 重新同步；这条正是"镜像永不命中"事故的形态 |
| `上游回落源不可达` | 公网源（GitHub）当前不通 | 有镜像站时只是 ⚠️；**没有镜像站时这一步就装不上** → 补镜像 |
| `上游返回 HTTP 404` | 回落源的地址已经失效（Typecho 的 jsdelivr 备址就是这样） | 换地址（改 `catalog.go`）并同步改声明 |
| `**没有超时**` | 声明里写了确实没有超时 | 要么给代码加超时，要么在界面上明说"这一步面板不管" |
| `声明里有 X，但目录里没有` / `目录里有 X，但没有声明` | 反漂移 | 两边同步：加应用必须同时填空 |
| `声明的 BrewFormula/ComposeImage/... 与目录不一致` | 反漂移 | 以目录为准改声明（或反过来，但要一起改） |

**static 门禁报错时不要改门禁，改数据。** 门禁本身在
`MarketDeclarationProblems()`；如果它误报了，那是门禁的 bug，单独修它并补测试。

## 哪些事仍然必须真机做

静态门禁 + 在线审计覆盖不到的事（**诚实的边界**）：

1. **"服务起不起来"**：审计只能证明文件下得到、manifest 里有 arm64，证明不了
   launchd 注册成功、端口没被占、进程没崩。→ `make market-audit-verify`
2. **真实安装耗时**：审计量的是"前 1 MiB 的吞吐"，不是"整包装完要多久"。
3. **依赖闭包的真实体积/成功率**：`brew install ffmpeg` 会拉十几个瓶、`pip install iopaint`
   会拉 torch（约 1~2 GB），审计只看根包。
4. **Docker 完整 pull**：审计走 registry manifest API，不走 `docker pull`，
   所以拿不到"层解压后多大、是不是真的跑得起来"。
5. **前端子路径能不能用**：`AppUI.Rewrites` 对不对，只有浏览器能说了算
   （历史上 Uptime Kuma 的页面标题对、请求全 200、正文却是 Page Not Found）。
6. **首次安装之外的状态**：升级、重装、卸载后重装、机器重启后的自启。
7. **没有第二台真机可验**：mini 已转生产、本机是唯一的开发与测试机；需要另一台机器的结论只能标"未验证"。
8. **镜像站的 `@pull` 回退**：CLT 载荷探到 HTTP 200 **不等于**已本地预置 ——
   镜像站会现拉现给。看到吞吐只有几百 KB/s 才说明它在回源。

## 附：常用命令

```bash
make market-audit-offline                        # 静态门禁（不联网，秒级）
make market-audit                                # 全部在售应用（在线）
make market-audit ARGS="--only squoosh"          # 只审一个
make market-audit ARGS="--json" > /tmp/a.json    # 机器可读
```
