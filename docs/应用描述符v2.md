## 1. 设计原则（硬约束）

1. **不引入外部 DSL 解析器 / 模板引擎。** `steps` 就是 Go 结构体（编译期类型检查）；
   模板只做 `{token}` / `{user}` / `{password}` / `{root}` 这类**字面量占位符**替换，
   不用 `text/template`（那会多一类只在执行期才暴露的解析错误）。
2. **不改变任务的对外契约。** 仍然 202 + `task_id` + SSE，进度仍走
   `result.step` / `emit`（`progress.go`）。描述符只改"实现放在哪"。
3. **老目录条目继续可用。** `App` 的 24 个字段一个都不动；描述符是"安装流程"的补充。
4. **单一事实来源。** 一个应用的参数（repo/tag/asset/端口/label/配置模板）
   **只写一份**。本轮 `releaseBinaryApps` 由描述符派生的方式见 §4.3。
5. **失败即 error。** 任何步骤失败都中止安装；唯一允许 "失败但继续" 的路径是
   **显式降级**（必须写 `DegradeReason`），对齐 `ready.go` 的 `assertReady`。
6. **不联网、不碰真实 launchd 的单测。** 执行器的副作用全部收在 `Runner` 接口后面。

## 2. 字段规范

### 2.1 顶层

```go
type AppDescriptor struct {
    ID             string          // 与 catalog.App.ID 一致（市场点击传的就是它）
    Name           string          // 展示名（任务日志、服务记录）
    Icon           string
    Category       string
    Rail           Rail            // brew | tarball | compose | pip-venv | panel-installer | site
    Kind           Kind            // 装完之后谁托管：native | docker | compose | colima
    Port           int             // **协议口**（安装前端口冲突检查用）
    Paths          DescriptorPaths
    Artifacts      []Artifact
    Steps          []InstallStep   // 流程本身（§3）
    Service        ServiceSpec
    Health         HealthSpec
    Inputs         []InputSpec
    Settings       SettingsSchema
    Uninstall      UninstallSpec
    Urls           Urls
    Notes          []string
    PanelInstaller string          // 与 App.PanelInstaller 对齐（已安装判定/卸载分流）
    ServiceLabel   string          // 与 App.ServiceLabel 对齐
    ChecksumArtifacts []Artifact   // 校验清单（镜像模式下由镜像站清单替代）
}
```

`Rail` 是"**怎么把它弄到磁盘上**"，不是"装完谁托管它"（那是 `Kind`）：
tarball 轨装出来的东西 `Kind=native`。`panel-installer` 轨是给
"要改 nginx / 建站点 / 写数据库"的复合流程留的（见 §5 的迁移判断）。

### 2.2 `Paths`

```go
type DescriptorPaths struct {
    RootDir    string // 安装根目录，**相对真实用户家目录**（如 "frpc"）
    Binary     string // 解压后的可执行文件名
    ConfigFile string // 配置文件名（相对安装根目录；空 = 没有独立配置）
    OutLog     string // launchd 标准输出（相对安装根目录）
    ErrLog     string
}
```

### 2.3 `Artifacts`（含 **arm64 证据字段**）

```go
type Artifact struct {
    Name            string           // 落盘文件名，也是镜像布局里的文件名
    Version         string           // **写死**的版本（跟 latest 漂会静默装错东西）
    URLs            []string         // 优先级：镜像 → 官方 → 第三方加速
    Kind            ArtifactKind     // tar.gz | zip | binary
    ExtractMember   string           // 只挑这一个成员（空 = 全部）
    StripComponents int              // 剥掉顶层目录层数
    Arm64           *Arm64Evidence   // ★ 架构证据
    Checksum        *ArtifactChecksum
    Required        *bool            // 默认 true
}

type Arm64Evidence struct {
    Evidence string // 观测到的事实（"Mach-O 64-bit executable arm64"）
    Source   string // 怎么核对出来的（"2026-09-16 实下解压后 file -b"）
    SHA256   string // 有就写上游清单里的值
    Size     int64
}
```

**为什么 arm64 证据必须是结构化的字段**：Asset 名里有 `darwin_arm64`
**不等于**内容一定是 arm64 —— 上游改过命名、挂错产物都真的发生过，
而症状是 launchd 报 `Bad CPU type`，完全指不到 "下错架构"。
所以 `Arm64` 字段落证据，安装时还有 `verify_arm64` 步骤在**运行期再复核一次**
（`file -b` 里必须出现 `arm64`，否则中止；铁律：不许 amd64、不许 Rosetta）。

`StripComponents` / `ExtractMember` 是真机踩出来的：frp 的 tarball 里
有 `frps`/`frpc`/示例配置（剥 1 层、只挑 `frpc`）；ddns-go 的 tarball
**没有顶层目录**（剥 0 层、挑 `ddns-go`）。沿用"成员名一定带顶层目录"的
老写法会去找一个不存在的路径，解压直接失败。

`Checksum.Kind` 区分三种**强度不同**的校验，不许含糊：

| Kind | 含义 | 能防什么 / 防不住什么 |
|---|---|---|
| `upstream-list` | 上游 release 里的 checksums 文件 | 防传输损坏；清单与产物同源时防不住镜像作恶 |
| `mirror-manifest` | 镜像站的 `manifest.json`（`make sync-apps` 生成） | 镜像模式下唯一的内容校验 |
| 空 | 上游根本没有清单（Orbien 客户端） | 没有内容校验，只有架构复核（**如实说明**） |

### 2.4 `Service`（label / plist 模板 / 工作目录 / 环境变量 / sudo）

```go
type ServiceSpec struct {
    Manager      string     // "launchd-system" | "launchd-user"
    Label        string     // launchd label（空 = 描述符非法）
    PlistPath    string     // plist 的绝对落盘位置
    Template     *PlistTemplate // 默认 DefaultPlistTemplate
    WorkDir      string     // 工作目录（相对安装根目录；空 = 根目录）
    Env          []EnvVar   // 额外环境变量（PATH 已内置）
    RunAs        string     // "user"（默认，降权）| "root"
    RequiresSudo bool       // 注册这一步是否需要 root
    RunAtLoad    *bool      // 默认 true
    KeepAlive    *bool      // 默认 true
    OutLog       string     // 相对安装根目录（空 = launchd.out.log）
    ErrLog       string
    StdoutTail   string     // 失败时给用户看的日志（空 = ErrLog）
}
```

`RunAs="user"` 是默认，也是刻意的：服务要写自己的配置与数据目录，
用 root 跑会让这些文件变成 root 所有，用户改不动。
`DefaultPATH` 注入 `/opt/homebrew/bin`：LaunchDaemon 启动的环境里没有 Homebrew，
应用启动时找 `ffmpeg` / `python` 会找不到（真机踩过）。

### 2.5 `Health`（端口 / 路径 / 超时 / **失败语义**）

```go
type HealthSpec struct {
    Probe         HealthProbeKind // port（默认）| http | launchd
    Port          int             // 要等的 TCP 端口（**协议口**，不是界面口）
    Path          string          // HTTP 探针路径
    ExpectStatus  []int           // 额外的可接受状态码（默认 2xx/3xx 都健康）
    Timeout       time.Duration   // 默认 60 秒
    Degrade       bool            // true = 失败只算警告；必须写理由
    DegradeReason string
}
```

**失败语义（默认，不许改）**：超时即 error，错误信息由 `assertReady` 生成
（期望什么 / 实际什么 / 等了多久 / 已完成什么 / 还差什么 / 怎么办 / 日志尾部；
没有日志时**如实写"没有日志"**）。要降级必须 `Degrade=true` 且
`DegradeReason` 非空——理由为空时 `Validate()` 直接失败。

`Probe=launchd` 是给**不监听任何端口**的应用用的（orbien 客户端是纯出站连接）：
对它们 `waitPort(0, 60s)` 必然超时，每次安装都会误报一次。

### 2.6 `Inputs`（需要用户提供的秘密 → 任务中心限时输入）

```go
type InputSpec struct {
    Key       string
    Label     string
    Secret    bool          // 前端用密码框；值只进 Credentials，不进日志
    Required  bool
    Default   string
    Generate  string        // "random-hex-16" 等
    Timeout   time.Duration // 默认 60 秒
    BindTo    string        // 替换进哪个占位符，如 "{token}"
}
```

复用 `input.go` 的 `InputProvider` + 任务中心的 `WaitInput`
（装 MySQL 时"限时询问 root 口令"就是这条路）。语义：**绝不阻塞** ——
超时自动用默认值/随机值继续；秘密只出现在 `InstallResult.Credentials` 里，
**绝不进任务步骤与审计日志**（步骤会被折叠、会长期保存）。

### 2.8 `Settings`（schema：类型 / 默认值 / 是否秘密 / 校验）

```go
type SettingsSchema struct{ Fields []SettingSpec }

type SettingSpec struct {
    Key      string
    Label    string
    Kind     SettingKind // string | int | bool | secret | enum
    Default  any
    Required bool
    Options  []string    // enum
    Min, Max int         // int
    Validate string      // "port" | "path" | "url" | "nonempty"
    BindTo   string      // 替换进模板的哪个占位符
    Advanced bool
    Note     string
}
```

两个用途，缺一不可：

1. **设置界面由 schema 生成**（现状缺口：`servicePanel.js` 里每个应用一份手写表单）；
2. **安装前的输入校验**：`SettingsSchema.ValidateSettings` 对端口/枚举/范围做
   校验，非法值**直接 error** —— 把 `0` 或 `70000` 写进配置文件只会让服务
   起来后立刻退出，而那时错误信息完全指不到"是设置项填错了"。

### 2.9 `Uninstall`（保留 / 清理策略）

```go
type UninstallSpec struct {
    RemoveService *bool    // 默认 true
    DataPaths     []string // 勾选"删除数据"时删的目录（"{root}" = 安装根目录）
    KeepNote      string   // 默认保留时对用户说的话
}
```

`KeepNote` 必须点名"保留了哪些**有秘密的文件**"：frpc 的 `frpc.toml` 里有
token、`ddns-go.yaml` 里有 DNS 服务商的 API 密钥 —— 用户以为卸载就清干净了，
结果密钥还留在磁盘上，这是真实的安全问题。

### 2.10 `Urls` 约定（**绑定地址决定广告地址**）

```go
type Urls struct {
    BindAddress    string // 应用**真正**监听的地址："127.0.0.1" / "0.0.0.0" / "::"
    AdminPath      string // 管理入口路径
    ProxyURL       string // 面板反向代理入口（{slug}），空则必须写 Reason
    ProxyURLReason string
    DocsURL        string
}
```

`AdvertisedURL(host, port)` 的三种结果：

| BindAddress | 广告地址 | 为什么 |
|---|---|---|
| `127.0.0.1` | `http://127.0.0.1:<port>` | 只绑回环，广告 LAN 地址会让用户点开一个**连不上**的链接 |
| `0.0.0.0` / `::` | `http://<面板探测到的主机地址>:<port>` | 对外监听，广告本机地址会让用户以为只能本机用 |
| 一个具体 IP | `http://<那个 IP>:<port>` | 服务**根本不在**面板探测到的地址上监听 |

看不懂的绑定写法（主机名、空串）一律返回**空**：空是**结论** ——
调用方必须如实显示"无网页入口"，不许拿 host 顶上。

**`proxy_url` 缺失必须显式声明原因**（`ProxyURLReason` 非空），并且二者互斥。
这是硬要求：子路径反代不是万能的（Uptime Kuma 的 Vue 路由不认前缀、
MinIO 要设 `MINIO_BROWSER_REDIRECT_URL`、纯 CLI 根本没有界面），
"没有代理地址"是一个需要解释的决定，而不是可以静默留空的字段。
`AppDescriptor.Validate()` 会强制这一条。

## 3. `steps` DSL

### 3.1 步骤清单

| 步骤 | 关键参数 | 语义与**失败**语义 |
|---|---|---|
| `ensure_dir` | Path / Mode / Owner | 建目录并按需递归改归属。失败 → error |
| `download` | Artifact / DestDir / MirrorPreflight | 镜像优先 → 官方（`--max-time 150`）→ 加速镜像（300s）；先落 `.part` 再改名；**全部失败但磁盘上已有该文件**则用它继续（否则"手动下载放到 `<root>`"就是一句空话）。失败 → error |
| `verify_sha256` | Artifact / Expect / Source / SkipIfNoChecksum | 内容校验。**拿不到清单或哈希不符都中止**（静默跳过等于把"有校验"变成"看运气"）。`SkipIfNoChecksum` 只给"上游确实没有清单"的条目（orbien），并且会如实写一条日志 |
| `verify_arm64` | Path | `file -b` 复核必须是 arm64。不是 → error，并说清"面板只允许原生 arm64（不跑 Rosetta 转译）" |
| `extract` | Artifact / Dest / Member / StripComponents / BootoutFirst / **ExpectFile** | tar（`-xzf`）或 zip（`unzip`）解包并挑成员。`BootoutFirst` 在重装时先停旧实例（覆写正在执行的 Mach-O 会被系统杀掉）。**`ExpectFile` 断言解完之后文件真的在** —— tar 退出码 0 也可能什么都没解出来。失败 → error |
| `copy` | From / To / Mode / Optional | 复制文件或目录树。`Optional` 需写明 Note，且只写一条说明 |
| `write_file` | Path / Content / Mode / Overwrite / Owner / Optional | 写文件。**`Overwrite` 默认 false**：配置里往往有用户填的密钥，默认覆盖等于把数据冲掉 |
| `ensure_config` | Path / Template / PreserveExistingConfig | 生成配置（含面板随机凭据）。判据在**执行那一刻**读盘：含面板 marker 则保留；`PreserveExistingConfig` 退化成"存在即保留"（ddns-go 的网页界面会抹掉 marker）。生成的 token/口令进入 `InstallResult` 的凭据区块 |
| `run` | Cmd / Args / As / Timeout / Env / Retries / AllowFailure | 执行命令（**命令与参数分开传，不接受 shell 字符串**）。默认 `As=user`（brew/pip/curl 拒绝 root）。`Retries` 只对幂等命令开放；`AllowFailure` 需写 Note（重装前 bootout 就是这一类） |
| `chmod` / `chown` | Path / Mode / Owner | 权限与归属。解压出来的权限来自归档（可能 0644），必须显式 0755，否则 launchd 报 "not executable" |
| `wait_http` | URL / ExpectStatus / Timeout | 等 HTTP 就绪；默认 2xx/3xx 健康 |
| `pip_install` | Python / Packages / IndexURL / **Verify** | venv 里装包；索引镜像站优先、回落官方。`Verify` 是"装完之后真的能 import/跑一遍"—— pip 退出码 0 不等于可用 |
| `pull_model` | Repo / Dest / Files / SHA256 / MD5 | 拉模型权重（需要执行器注入下载器；没接入就**明确失败**，绝不跳过） |
| `create_db` | Name / User / Password / Charset | 建库建账号（同样需要注入，没接入即明确失败） |
| `seed_site` | Source / Dest / Overwrite | 铺站点文件；默认不覆盖已有站点 |
| `register_service` | Label / Name / Icon / Category / Port | 登记进「服务管理」。**登记失败不让整个部署失败**（刻意的降级：服务是好的，只是列表里暂时没有它） |
| `write_plist` | Args / Template | 渲染并写入 plist（先 `.tmp` 再 rename）。Args 第一项通常是 `{root}/<binary>` |
| `launchd_bootout` | Label | 幂等卸载旧实例（本来没有也算成功） |
| `launchd_bootstrap` | Label / Plist / Message | 装载并启动；等旧实例真的消失再装（`launchctl bootout` 是异步的） |
| `assert_ready` | What / State / Missing / Remedy / LogPath | 就绪判定，**失败即 error**（要降级必须在 `Health` 里显式声明理由）。必须排在 `register_service` **之后**：验收如实失败时，登记留在后面会留下"任务失败、服务管理里又找不到它"的半成品 |
| `message` | Lines / Secret | 只写进度。`Secret=true` 的文本只进凭据区块，不进步骤叙述 |

### 3.2 执行器与可测性

`ExecuteInstall(ec *ExecConfig)` 顺序执行步骤，第 i 步失败即返回
`「<name>」安装失败（第 i 步 <kind>）：<原因>`。所有副作用都收在
**`Runner` 接口**后面（`Stat/MkdirAll/WriteFile/SHA256/ChownTree/CopyTree/
FileType/RunAsUser/RunRoot/Bootout/Bootstrap/LaunchRunning/WaitPort/HTTPGet/PrimaryIP`）：

- 生产实现 `sysRunner` 直接调 `os/*` 与 `launchctl`；
- 单测注入 `fakeRunner`，于是"下载 → 校验 → 解压 → 落盘 → 注册 → 验收"
  **整条编排**可以在 `t.TempDir()` 里、不联网、不碰 launchd 地验证。

需要外部能力的步骤走 `ExecConfig` 的钩子，**没接入就明确报错，不静默跳过**：
`MirrorPreflight` / `VerifyMirror` / `FetchChecksumList` / `RegisterService` /
`PipIndexURL` / `PullModel` / `CreateDB` / `UnregisterService`。

## 4. 第一轮实现：tarball 轨

### 4.1 迁移前后对照

| 老实现（`binary_release.go`） | 描述符 v2 | 行为是否一致 |
|---|---|---|
| `releaseBinaryApps` 参数表（12 字段） | **保留**（参数仍只写一份），描述符由它派生 | 一致 |
| `binaryReleasePaths()` | `AppDescriptor.Paths` + `binaryReleasePathsFor()`（由描述符推导） | 一致（老函数保留为壳，内部查描述符） |
| `preflightMirrorAsset` + `downloadReleaseBinary`（~80 行） | `download` 步骤 + `MirrorPreflight` 钩子 | 一致：镜像优先、官方 150s、镜像 300s、`.part` 改名、磁盘已有产物退路 |
| `verifyMirrorChecksum` / `verifyReleaseChecksum` | `verify_sha256` 步骤 + `VerifyMirror` / `FetchChecksumList` 钩子；`mirrorUsed` 决定用哪套哈希 | 一致：**做镜像预检的那一次下载**决定了后续用镜像清单还是上游清单（`verifyMirrorChecksum` 已改为委托 `mirrorChecksumFor`，期望值只有一份取法） |
| `extractArgs()` 拼 tar 参数 | `extract` 步骤 + `tarExtractArgs()`（同一份实现被两处调用） | 一致（含 frpc 剥 1 层挑成员、ddns-go 剥 0 层） |

| `ensureReleaseConfig()` + `writeConfigSeed` | `ensure_config` 步骤（判据函数 `configKeepsExisting` 复用） | 一致：marker 判据 / ddns-go "存在即保留" |

| `waitReleaseBinaryReady()` | `assert_ready` 步骤 + `HealthSpec` | 一致（端口 / launchd 两类判据、失败即 error、日志尾部） |

### 4.2 关键改动：让描述符**变成**事实来源，而不是第二份副本

- `releaseBinaryApps` 里的展示字段（Name/Icon/Category/Label/Port）在 `init()`
  里由描述符回填，两边不可能漂。
- `InstallReleaseBinary` 变成兼容壳：**只做前置校验 → 装配执行器 → 执行步骤**。
  对外签名与任务契约一字未改（`internal/web` 一行都不用动）。
- 已被 `steps` 覆盖的旧私有函数（`downloadReleaseBinary` /
  `verifyReleaseChecksum` / `verifyArm64Binary` / `orderDownloadURLs` /
  `waitReleaseBinaryReady` 的内联探针）**直接删除**，不留两套实现各说各话。
- 仍被别处消费的私有函数保留为薄壳（`binaryReleasePaths` /
  `extractArgs` / `ensureReleaseConfig` / `releaseBinaryPlist` /
  `waitReleaseBinaryReady` / `UninstallReleaseBinary` / `releaseBinaryPlan`）。

### 4.3 加一个新 tarball 应用要做什么

1. 在 `releaseBinaryApps` 里加一条参数（repo/tag/asset/启动参数/配置模板/说明）；
2. 在 `tarballDescriptors` 加一行 ID。

不需要新写 `InstallXxx`，不需要改 `internal/web`。步骤序列由
`tarballInstallSteps()` 统一生成。`TestNewAppInstallsFromDescriptorAlone`
就是这条承诺的可执行证明（§6）。

### 5.2 逐条说明（需要新字段的部分）

- **frpc / orbien-client / ddns-go（本轮完成，3 条）**
  `当前实现文件/函数`：`binary_release.go` 的 `InstallReleaseBinary`（本轮已改为
  "描述符 → steps → 执行"）。
  `目标 rail`：tarball。`用哪些 steps`：
  `ensure_dir → download(×(1~2)) → verify_sha256 → extract → verify_arm64 →
  chmod → ensure_config → chown → write_plist → launchd_bootstrap →
  register_service → message → assert_ready`。
  `还缺哪个字段`：无（`Artifacts.Arm64`、`Urls.BindAddress`、`Urls.ProxyURLReason`、
  `Settings`、`Uninstall.KeepNote` 在本轮新增）。

- **compose × 9（零代码）**
  现有 `ComposeYAML` 就是数据。迁移只需把"写 compose 文件 → `compose up -d`
  → chown → 登记"表达成 steps（`write_file` + `run` + `chown` +
  `register_service`），并且**镜像加速源检查**（`EnsureDockerMirrorsForRuntime`）
  要与 colima 轨共用同一个前置步骤。
  `还缺哪个字段`：`artifacts.images[]`（逐条核对 arm64 / registry 来源，
  现在靠 `composeImagesOf` 运行时解析）。

- **brew × 6（零代码）**
  nginx / php81-84 / mysql84 / ffmpeg：`installViaBrew` 已经是通用的。
  steps：`brew_ensure` + `brew_services_start` + （PHP）`assign_php_endpoint` +
  （MySQL）`init_datadir` + `register_service`。
  `还缺哪个字段`：无（`BrewFormula` / `ServiceLabel` / `HealthPath` 已在目录里）。

- **ollama**
  缺 `pull_model` 的"模型注册表"变体（ollama registry 与 HF 不同：
  要 `ollama pull` + 校验 manifest digest）。另外 `EnsureOllamaModel`
  是"安装后动作"，需要一个 `post_install_steps` 的概念（或把拉模型做成
  `run` 步骤 + `assert_ready` 判 `/api/tags`）。

- **docker-runtime（colima）**
  缺新 rail `colima`：`brew_ensure(colima)` + `run(colima start)` +
  `EnsureDockerMirrorsForRuntime`（配 registry-mirrors + 重启运行时）+
  `register_service`。它是所有 compose 应用的前置，必须在描述符里可表达。

- **iopaint**
  `InstallIOPaint` 里通用执行器表达不了的部分（按重要性）：
  ① `freeDiskGB` 磁盘预检（需 `assert_disk_min_gb`）；
  ② `pickIOPaintDevice` 探测 MPS/CUDA（需"工具步骤返回类型化值 + 用户输入默认值"）；
  ③ `ensureIOPaintWeight` 的 MD5 校验 + 多源回落 + 停滞判定（需 `pull_model` 的
  `md5` + `stall_timeout`）；
  ④ `installIPv4Sitecustomize`（需 `patch_python` 或 `write_file` + venv 路径占位符）；
  ⑤ 安装结果需要回填 "device / weight URL"（需**类型化步骤输出**
  `StepOutput{string,int,bool}` —— 本轮只做了 `secrets` 这一种传递）；
  ⑥ `launchctl setenv HF_ENDPOINT`（需 `set_env` 步骤或 `Service.Env` + 进程环境）。

- **qwen3tts**
  同 iopaint 的 ①②③⑤⑥，另外：
  ⑦ `EnsureHomebrew` / `EnsureCLT` 依赖链（需 `ensure_dependency` 步骤：
  CLT → brew → `python@3.11`，三步各有自己的判定与镜像）；
  ⑧ `EnsureQwenModelsLoaded` 预热（需 `warm_model` + `assert_ready` 的 JSON 探针）；
  ⑨ 绑定地址由"是否启用鉴权"决定（`QwenOptions.Auth`）—— 需要
  **条件步骤**（`when`），或者把"是否鉴权"做成 `Inputs`/`Settings` 的一项，
  由构造期展开成两条描述符分支。本轮**没有**做条件步骤，这也是它无法只靠
  描述符表达的原因之一。

- **voicereceiver**
  ⑩ Python 脚本部署（`voice-receiver.py` 内嵌在二进制里）→ 需 `write_file`
  配合 embed 资源，或者 `copy` 从 `/opt/zizpanel/...`；
  ⑪ 共享密钥（可指定或随机）→ 正好是 `Inputs` + `Generate` 的用例；
  ⑫ `assertReceiverKeyUsable`（带密钥调用一次 `/v1/...` 断言）→ 需
  `assert_http` + 头部注入；
  ⑬ 音色样本目录**必须保留**（卸载默认不删）→ `Uninstall.DataPaths` 要区分
  "二进制/venv" 与 "用户数据"（现在 `KeepNote` 说得清，但 `DataPaths` 只有一个列表）。

- **phpmyadmin**
  ⑭ `brew install phpmyadmin` → `install_package`；
  ⑮ 写 nginx `location /phpmyadmin/`（`SelfConf=true`）→ `nginx_location`；
  ⑯ 依赖检测 php-fpm 与 nginx → `assert_dep`；
  ⑰ 拷 `config.inc.php` 并注入随机 blowfish secret → `write_file` + `Inputs`；
  ⑱ 验收要判**页面内容**而不是 200（历史坑：phpMyAdmin 的错误页也返回 200）
  → `assert_ready` 的 `ProbeHTTP` 需要"期望正文片段"字段。

- **lnmp（组合动作，不是目录条目）**
  `InstallLNMP` 是"三包 + 四件收尾"的复合事务：`brew_bundle`、
  `patch_nginx_conf`（改 `listen 80`、建 vhosts include）、
  `init_datadir`（MySQL 初始化 + 生成 root 口令 → `Inputs`）、
  `assign_php_endpoint`、`register_system_service`。
  这些都能做成步骤，但**事务性**（失败要不要回滚已装的两个包）需要新语义。

- **typecho / wordpress**
  当前**不在** `internal/services`：走 `internal/web` 的建站流程。
  本轮按分工要求**不改** `internal/web`，所以这里只给迁移方案：
  目标 rail `site`，steps = `download` → `extract` → `seed_site` →
  `create_db` → `write_vhost` → `assert_ready(HTTP)`；缺 `write_vhost`、
  `create_db`（未接入实现）、`Inputs`（站点域名 / 库口令）。

### 5.3 用一句话回答"哪些必须写代码"

**能零代码迁的 18 条**（tarball 3 + compose 9 + brew 6）覆盖了绝大多数"上架"需求。
**必须新增字段/步骤的 9 条**集中在三类：
① 需要"步骤之间传值"（pip-venv 两个 AI 应用）；
② 需要"探测结果决定后续动作"（条件步骤 / 类型化输出）；
③ 需要"改系统配置"（nginx / PHP 端点 / MySQL 数据目录 / colima 运行时）。

## 7. 明确**不做**的事

1. **不引入外部 DSL 解析器 / 模板引擎**（不用 yaml/toml/jsonnet 描述流程，
   不用 `text/template`）。
2. **不改变现有任务的对外契约**：202 + `task_id` + SSE + `result.step` 一字不动。
3. **老目录条目必须继续可用**：`App` 的 24 个字段不动；
   老函数名（`InstallReleaseBinary` / `UninstallReleaseBinary` /
   `binaryReleasePaths` / `ensureReleaseConfig` / `releaseBinaryPlist`）
   保留为壳，但内部**只有一份实现**。
4. **本轮不改 `internal/web/**`、`site_sources.go`、前端 JS**：
   站点类（typecho / wordpress）与需要 web 层分流的改动只写进本迁移清单。
5. **不做条件步骤 / 循环 / 变量作用域**：本轮只支持"顺序执行 + 秘密传递"，
   这是 iopaint / qwen3tts 还不能纯描述符化的直接原因（见 §5.2）。
6. **不动 `site_sources.go` 的站点源**：站点类应用的描述符化排在下一轮。
